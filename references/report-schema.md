# report.json：只写本次消息支撑的内容

群名、日期、时长、消息数、发送者数和媒体数均来自同目录 `messages.json`。不要在 report.json 中重复填写这些统计，以免下一次复用仍显示旧日期或旧群名。

```json
{
  "intro": "用两三句话概括本期主线和最需要关注的事。",
  "topics": [
    {
      "title": "话题及实际进展",
      "paragraphs": ["概括谁讨论了什么。", "保留后续结果、限制和未确认项。"],
      "message_ids": [1, 3, 8]
    }
  ],
  "followups": [
    {
      "title": "需要跟进的问题 · 当前状态",
      "paragraphs": ["区分成员明确承诺与报告建议，并写清缺少的答案或验证。"],
      "message_ids": [9, 12]
    }
  ],
  "resolved": [],
  "other": []
}
```

示例编号仅展示类型，必须换成本次真实编号。四个章节都是数组，条目结构相同：`title` 非空字符串、`paragraphs` 非空字符串数组、`message_ids` 非空整数数组。无内容的章节用空数组，不为凑栏目编造待办。每个引用都必须来自本次导出；渲染器会拒绝不存在的编号，但语义是否支撑内容仍由 Codex 核对。

`intro` 必填。读取到零条消息时四个数组都为空，intro 说明没有本地记录，提示无法从中推断手机或整个群的实际活跃度。仍正常生成 PNG、网页和 Markdown。

建议报告保持可读的 3–6 个主要话题，实际数量由记录决定。条目可有多个段落；用不带 Markdown 标记的纯文本，以便 PNG 与 HTML 同文渲染。来源编号由程序格式化，勿另把来源揉进每段正文。完整聊天文本仍在 messages.txt，报告只放必要摘要。

一条内容被多条连续消息支持时，列举这些真实整数，不能写字符串范围 `"1-12"`。媒体只有标记时可引用其编号证明“分享了图片”，不能借它描述未识别的图片内容。

来源说明写在报告底部；不要将手机号、完整账号标识、内存地址、密钥或本地数据库路径抄进对外报告。人名与群昵称按任务需要保留。消息里的“我”只在本机配置有明确 self_name 时对应那个人，否则保留原称呼。
